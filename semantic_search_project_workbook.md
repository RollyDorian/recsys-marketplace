## О проекте

**Бизнес-контекст.** Компания CalmFruits развивает онлайн-каталог товаров. Пользователи ищут товары через поисковую строку, но классический поиск по ключевым словам не всегда хорошо справляется с реальными пользовательскими запросами.

**Гипотеза.** Команда хочет проверить, можно ли улучшить поиск с помощью векторных представлений запросов и товаров. Для этого нужно построить MVP системы семантического поиска.

**Ваша роль.** Вы выступаете в роли DS-специалиста, который получает каталог товаров и историческую разметку релевантности товаров. Ваша задача - построить базовую систему поиска, сравнить несколько подходов и объяснить бизнесу:

- стоит ли использовать векторный поиск;
- в каких случаях он помогает, а когда ошибается;
- какие улучшения стоит рассмотреть дальше.

**Данные.**

В проекте четыре файла. Три из них - рабочие, к ним вы будете обращаться постоянно, один - служебный, нужен для одного этапа проекта.

### Финальные требования к проекту по итогам QA-сессии

По итогам QA используем следующие правила поиска и оценки.

1. Объект поиска - карточка товара, связь разметки по imt_id.
2. Из чего формируется выдача при оценке качества: общий каталог из пула wb_products_dedup; тексты из raw.
3. Как трактуются товары, отсутствующие в разметке для запроса: relevance = 0, по шаблону ноутбука.
4. Главные метрики и значения K для принятия решения: порог relevance >= 2 подтверждён в pt.2; в примере показаны K=5 и K=10. Для базового сравнения считаем все пять метрик при K=1,3,5,10; результаты сравниваем по NDCG@10 и Recall@10.
5. Что делать с товарами без описания: оставить с названием; удалить только полностью пустые тексты.
6. Прочее: финальный test и логирование экспериментов относятся к неделе 3.

## 2. План базового пайплайна

**2.1. Формулировка задачи своими словами**

В 3-4 предложениях опишите, что ищете, по каким данным, как оцениваете результат и зачем это бизнесу.

По текстовому запросу возвращаем подходящие карточки imt_id. Используем названия, категории и описания товаров одежды и обуви. Сравниваем TF-IDF и компактную мультиязычную модель на общем пуле оценки по синтетическим train-запросам. Цель - проверить, полезен ли семантический поиск для каталога, и определить направления улучшения базового решения.

**2.2. Подготовка данных** 

Одежда и обувь; дедупликация по самому длинному описанию с устойчивой сортировкой по nm_id. После неё 48 489 карточек; 113 без текста удалены, осталось 48 376. Каталог оценки - все 4 256 imt_id пула. Product_text: название, категория, описание; HTML, URL и повторные пробелы очищены, бренд исключён.

**2.3. Лексический поиск (baseline)**

TF-IDF с ngram_range=(1,2), max_features=50000. Индекс обучен на подготовленных текстах без использования оценок. Поиск - косинусное сходство; полный и ограниченный каталог используют один словарь и IDF.

**2.4. Семантический поиск**

paraphrase-multilingual-MiniLM-L12-v2 через SentenceTransformer, 384 признака, L2-нормализация. Эмбеддинги считаются батчами по 16 и сохраняются в .npy. Лимит модели - 128 токенов, его превышают 28.05% карточек.

**2.5. Оценка качества** 

Все пять метрик при K=1,3,5,10, бинарный порог 2. NDCG использует gain=2^rel-1, MRR - полное ранжирование. Train/test не пересекаются. Test не использован для настройки.

**2.6. Результаты базового сравнения**

TF-IDF: train NDCG@10=0.4315, Recall@10=0.2869, Precision@5=0.0697, MRR=0.1769. Семантика: NDCG@10=0.1512, Recall@10=0.1378, Precision@5=0.0480, MRR=0.1233. На текущем этапе TF-IDF лучше по всем этим метрикам. В запросе топы cop copine лексика возвращает топы, а семантика - пуловеры и кофты. В запросе худи mego as семантика показывает худи только на пятом месте. Для бриджи зуавы лексика возвращает бриджи, а семантика смешивает обувь и одежду. Бренды отсутствуют в базовом тексте по QA; для таких запросов нужен отдельный фильтр. На следующем этапе можно проверить другой шаблон текста, нормализацию слов и гибридный поиск.

- опишите сводную таблицу метрик;
